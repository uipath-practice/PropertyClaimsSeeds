# Verify

Every piece was checked as you built it. **Does the whole thing work as expected?**

`PDD.md` §13.2 lists the problems a real claim arrives with, and §1.3 says what success means numerically. 
- Run six clean claims **first**, across different claimant profiles — with fewer, one false escalation reads as a third of them against SC5's one in ten
- Then aim a run at each claim problem in turn, and record what happened against both. 
- Run them together as one batch, and every later batch whole, with fresh seeds for its clean claims — a fix is proven only on claims it was not tuned on: over-flagging a clean claim is the failure that reappears, and a fix that closes one problem can open another.

**Now you may read the answer key.** 
- It sits beside the documents in the `Claims` bucket and states what was planted and what should happen — the oracle you have been forbidden until this point. `contracts/provided-processes.md` names it.
- Read it as a record of what was *injected* into the documents, not of what the arithmetic must produce. A failure that no injector plants is a false positive (`cookbook.md`). Its `Gateways` names the gates the planted problem opens **before any human answers** — a screening failure your eligibility reviewer proceeds past must also open claim review, by `PDD.md` BR-40; the key does not model the reviewer, the PDD does.

Four things to establish:

- **Each planted problem is caught by the Agent that owns it, and stops the claim at the right Action Center gate task.** Not caught by something else, and not caught twice: a reviewer seeing one problem reported by three Agents reads three problems.
- **A clean claim settles in full with no task ever raised** — not even an Action Center task whose checks are all green and whose recommendation is *approve*.
- **What the claimant is told matches what actually happened.** The letter recorded by `Client Notification` in the tenant-level `ClaimCorrespondence` entity (one row per letter keyed by claim id) states the decision and the figures the Data Fabric record holds. Read it from the entity, not from the job log. Read the paid figure from `decisionJson.outcome` against `status`, never from `settlementJson`: that column is what the settlement *computed*. Score each letter against the answer key's `LetterMustMention`: a concern a human ruled on belongs in the letter.
- **Two clean claims of one claimant profile settle to the same cent.** Start both with the same `profileId` (`claims-profile-01` … `12`) and compare every figure of the two records, not the prose; the same `seed` as well makes the documents identical, which tells agent variance from document variance, and **the answer key records the seed the generator drew even when you passed 0** — so any claim, planted or clean, can be regenerated byte for byte for a before-and-after (`cookbook.md`, *Two runs are not the same as two claims*).

Then check the build against the design rather than against the process: enumerate every stage, task, rule, SLA and variable in `sdd.md` and mark each **Implemented · Missing · Mismatch · Extra**. *Extra* is the one worth looking hardest at — it is what nobody asked for, no tool reports, and every reviewer pays for later.

**Three fix cycles, then score.** A cycle is one whole batch, every fix that batch shows, and one redeploy. Fix at the source, in the block that owns it. After the third redeploy, run the batch you score and stop fixing, whatever it shows — this is a working solution to hand over, not a production release, and `5-ship` reports what is still open. A run that finds nothing was probably not aimed. A case plan change reaches only instances started **after** the redeploy; an agent change reaches the next call on any instance — so bump, deploy, then start the batch, never deploy into a running one and read half the change.

**Done when** the batch you score ran after your last redeploy, and it shows:
- per planted problem, which Agent caught it and which Action Center task showed it to a human — or why it is still missed and the fix you would make next;
- claims with nothing wrong settled untouched, with at most one in ten referred to a human (`PDD.md` SC5), each referral named with its cause.
