# Deploying the case and running it

## How it is built here

- **Aim each run** with the case's own `scenario` / `discrepancy` inputs, and `profileId` to repeat a claimant; they flow to the generator (`contracts/provided-processes.md`, *Retrieve Property Claim*). Pin a `discrepancy` with every scenario, preferably an unambiguous breach (rows below).
- **Decide gate tasks with `uip tasks complete`** (the row below has the shape). The app has only its empty registration page.
- Five runs prove the block: one clean, four routes. Start one claim on each new version before the batch.

**Compile before you pack** (`uip maestro case pack`, as the case skill says), and check the compiled `caseplan.case.bpmn` is inside the case nupkg before you deploy.

## Deploying

| Issue | Fix |
|---|---|
| `deploy run` refuses: the package is already deployed | Upgrade in place (`uipath-solution`), or `deploy run --config-file <config> --name <the same name> --yes`, which updates the named deployment in place; read the installation back to confirm it is still one deployment (`CONFIG.md`, *Deploying*). `Key` rotates on every version change and `upgrade` refuses `InstallDeploymentKey`, so re-read `Key` from `deploy list` first. |
| A case will not start: *Invalid package key format*, *Release key is required* | `uip maestro case process run "<dotted PackageId>" <folder-key> --release-key <release GUID> --inputs '{…}'`. The release GUID comes from `uip or processes list --folder-key <deploy key>` (`uip maestro case process list` answers a generic error), and `--validate` rejects every shape the run accepts. The returned `JobKey` is the instance id. `uip or jobs start` takes the process `Key` GUID; the dotted `ProcessKey` fails as *Undefined process*. |
| `deploy uninstall` answers `Validation failed.` and nothing else | A job is not final — the CLI drops the Solutions UI's *Jobs are not in final state yet*. List the solution folder's `Running` / `Pending` / `Suspended` / `Stopping` jobs (`uip or jobs list --folder-key <solution folder key>`), `uip or jobs stop <job-key> --strategy Kill`, and uninstall again; a case instance reading `Completed` proves nothing. A `deploy run` that never installed is removed only in the Solutions UI (`CONFIG.md`, *Deploying*). |
| Every record write fails after a clean deploy: an unauthenticated connection | The deploy config declares the Data Fabric connection at `solution_folder` and mints a copy nobody consented to. Before the first `deploy run`: `uip solution deploy config link <config> "Shared Data Fabric Connection" --name "Shared Data Fabric Connection" --folder-path Shared`. An upgrade keeps the link. **Link every provided process the solution lists as a resource too** — `resources refresh` and `case spec` add them, and an unlinked one is installed as a copy in `-Deploy` that the case calls instead of yours (Extract Claim Data then faults *Bucket Not Found*, 170002): `uip solution deploy config link <config> "<process name>" --name "<process name>" --folder-path ClaimCase-<seat>` for each, then check `uip or processes list --folder-key <deploy folder key>` holds only the case and its agents. An `app` or an entity resource links locally and the server refuses it (*ResourceKindDoesNotSupportLink*): `deploy config unlink` it. An unlinked entity is installed as a twin in `-Deploy`, and **a write that carries an entity root binding writes to that twin**: give every record write the literal entity name and seat folder key, with no entity binding, and before every publish check the package holds the case and seven Agents and no `entity` or `app` resource (`resources refresh` and `solution pack` re-import both). Take an `app` resource out of the solution (`3d-case/cookbook.md`). |
| You are running the deploy loop for the fifth time by hand | Script it: bump → `case pack` → `solution pack` → `publish --wait` → `deploy upgrade` → start a claim → read the record. `set -e`, and **assert the four things that lie**: the compiled `caseplan.case.bpmn` is inside the case nupkg; exactly one deployment carries the pinned name; `deploy list` shows the new version `Successful` and `Active`; the Data Fabric record (not the job status) shows the write. Time each step into `PROGRESS.md`. A deploy takes under a minute and a claim 7–14. On a new version, start one claim first and let it pass its first record write before starting the rest. |

## When a claim does not do what you expected

Read the instance, not the job list. The `uipath-maestro-case` troubleshooting guide has the commands. What it leaves out: `instance variables` returns the case globals as one merged `Globals` map, and `CaseLocalLatestCaseState` holds only the latest transition — the timeline is `uip maestro case instance element-executions`. A case job stays `Running` after its instance completes; `or jobs list` is not newest first, so filter with `--created-after`. Task outputs are under `DataManager` and in the variable each output row writes; `tasksEventSubProcess[].TaskCompletedOutputsVariable` can hold null for a reassigned row. **An incident's cause is at the end of its detail**, not the start.

**A case job has no log** (`uip or jobs logs` returns zero rows) **and no trace** (`uip traces spans get --job-key`, zero spans). For an Agent or RPA fault, read the **child job**: `uip or jobs list --folder-key <folder>`, then `uip or jobs get <key>`, where `Info` carries the message. `instance list --folder-key` does not filter strictly by folder, so filter with `--package-id <dotted id>`.

| Issue | Fix |
|---|---|
| `uip tasks list` on the deploy folder returns 0 and there is no incident, so the gate looks silently broken | **The task appears in the folder that holds the app**, not the folder that holds the case. List the seat folder. |
| `uip tasks complete` says *This action is no longer assigned to you* on a task you never touched | Check `uip tasks get <id>` first: a task nobody holds needs `uip tasks assign <id> --user <email>`, one already held by someone else needs `reassign`; read the assignee back, since `assign` can report success and change nothing (neither takes `--folder-key`). Then `uip tasks complete <id> --type AppTask --action <Action> --folder-key <seat folder> --data '<the task's data, spread, with the outputs set>'` — `--type` is required, and `--data` replaces the whole payload, so an omitted field is erased. A task carries the case **instance** id (`CreatorJobKey`), not the claim id; `uip tasks data get` returns `RecordId`, `ClaimId`, `TriggerStage` PascalCased. |
| Route runs are eating the afternoon | Run the four human routes **concurrently**. Each mints its own claim id, and five claims in parallel take a quarter of an hour instead of an hour. |
| `scenario: eligibility-fail` did not open H1; `review-fail` settled itself | **A scenario does not guarantee a route.** Pin it with `in_Discrepancy`, paired with its scenario. An unknown id faults and lists the valid ones (`contracts/provided-processes.md`). A pin plants the problem but the Agent still judges it, so prefer an unambiguous breach (`ELIG_POLICY_LAPSED`, `ELIG_IDENTITY_MISMATCH`, `REVIEW_AMOUNT_INFLATION`) and keep a spare claim in flight. **Before you count an aimed run, check the pin reached the generator**: the generator job's `InputArguments` (`uip or jobs get <job key>`) must carry the `in_Discrepancy` you meant — a script that drops it gets a random claim and reports success. The answer key stays unread until Verify. |
| A claim faults with `170002` | It is either the LLM provider (several claims within seconds, `HTTP Request Failed`) or a real case defect — a required activity argument left unbound names the argument (*Value for a required activity argument 'in_…'*). The child job's `Info` tells them apart. A provider fault recovers in place: `uip maestro case instance retry <id> --folder-key …`. *License not available for LLM usage* on many claims at once, and a retry refused with `PIMS-400504`, is the tenant's Agent Unit allocation: stop starting claims, ask your operator to raise it, then retry each faulted instance in place. |

## What only a run shows

| Issue | Fix |
|---|---|
| The very first record write faults with `Value uniqueness violation … Error Number: 2627` and names nothing you recognise | `claimId` is unique (`contracts/claim-entity.md`). If the claim id was reused, delete its row first: `uip df records query … --folder-key`, then `records delete`. If it happens under concurrency only, one claim in four, it is the double start in the next row. |
| `Client Notification` jobs are `Successful` and the `ClaimCorrespondence` entity has no row for the claim | The robot cannot write the entity; the job logs a warning and succeeds. **The proof of a letter is its row in the entity**, never the job status. A missing grant is your operator's to fix. |
| Under concurrency, a write runs twice, or every claimant gets two identical receipt letters (sometimes unaddressed: *Dear ,*), and instances carry `450007 Duplicate message subscription` | A `runs-sequentially` task after a parallel group starts once per predecessor when the predecessors finish within a fraction of a second. A `selected-tasks-completed` fan-in fires once. A `runs-sequentially` task after the fan-in still double-starts, silently. Fix it in the plan: `3d-case/cookbook.md`, *What only a run shows* (no `runs-sequentially` in a stage with a parallel group or a fan-in). The tell is the row count per claim in the tenant's `ClaimCorrespondence` entity. Timelines and instance status both say everything is fine. |
| Which incident codes matter | `102003 Integration Services bad request` is a real fault on a task you wrote. `450007` and `450013` on the compiler-generated `*_CancelTaskBoundaryEvent` and `stopStageSlaMessageEvent_*` elements are noise on their own, and a symptom when letters or writes come in twos. A `450006` after a completed task can hide a fault further down the claim: read the incidents again after every retry. |
| Every claim faults at its first record write with *Entity 'ClaimCase_<seat>' not found at tenant level*, and nothing in your build changed | The connector renamed a `PREVIEW` V3 parameter. `3d-case/cookbook.md`, *Writing to a folder-scoped entity*, has the arbiter. Bump and redeploy. A running instance keeps the version it started on, so recover each one in place: `uip maestro case instance migrate <id> <version> --folder-key <deploy folder>`, then — once the instance has left `Upgrading`, about 20 s; earlier is refused with `PIMS-104002` — `uip maestro case instance retry <id> --folder-key …`. Run one instance per command: a loop reads as a shared-resource change to a harness classifier. Migrate an instance parked at a gate before completing its task, or recover it afterwards. |
| A claim that was running faults at an Agent after you deployed a new version | An upgrade keeps each instance on the case version it started on, but its Agent calls resolve against the deploy folder's current release. Recover each instance in place, `instance migrate` then `instance retry` (the row above). Upgrade between batches, not under one. |
| A polling loop overwrites a good result with a later empty one | A stage that re-enters re-runs its calls. **Guard the write**, or the next not-ready result replaces a ready one. |
| A stage never exits although the task's result is in | A reassigned output's **id** (`out_ReportReady`) reads null in a condition; only the variable it writes (`reportReady`) carries the value. Test the variable. `check_caseplan.py` warns on a condition that reads an output id. |
| A routing guard sends a claim down the wrong lane | A gate is evaluated before the output of the task that fired it is extracted, so read the variable that task's output writes, not a variable an earlier task left behind (`uipath-planner` `references/case/case-design-layers-guide.md`, *Gate on the producer*). **Test for the outcome you want, not against the one you don't**: `'' !== 'Deny'` is true, so an unset decision sends a denied claim down the approved path. |
| The approval letter quotes the pre-override amount | The review gate never rewrites the recommendation's scalar (`vars.netPayable`). Bind the correspondence Agent's amount, and the outcome's, to the **confirmed** settlement, which is the gate's output. |
