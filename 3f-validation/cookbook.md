# The Coded Action App — what bites

## Where the time goes

**Park your Action Center tasks before you start iterating.** Getting a claim to stop at a gate takes minutes; doing it again for every code change is the difference between a morning and an afternoon. Aim a run at a gate once, leave the task waiting, and rebuild against it.

**Match the loop to what you changed.** A style change does not need a redeploy; a schema change does. Redeploying for everything is most of the time this block costs.

| Issue | Fix |
|---|---|
| A local run looks like it has hung | Give it three seconds. It reliably looks dead just before it works. |
| A PDF will not display | Browser-native embedding is **blocked by the host's sandbox** — `<embed>`, `<object>` and `<iframe>` all fail. Use a JavaScript renderer. |
| The document panel says *Failed to fetch* while the claim record renders fine | **Your SDK is pointed at the portal host.** `cloud.uipath.com` answers CORS for Data Fabric and not for Orchestrator, so the record loads and the bucket call dies — a partial failure that reads as an Orchestrator policy and is not one: `https://api.uipath.com` answers the same preflight with `access-control-allow-origin: *` (measured 2026-08-28; `uipath-coded-apps` rule 8). The working shape, from a shipped app: `new UiPath()` **bare** with the host-injected session, `buckets().getByName(name, { folderId })` then `getReadUri(...)`, `fetch(uri)` on the pre-signed URL → blob → object URL, `react-pdf` with the pdf.js worker bundled from the app's own origin (the CSP blocks a CDN worker). Never diagnose CORS with a curl against the host the broken app is using. Classify a caught error before wording it (*unreachable* / *refused* / *other*) and put the file and bucket name on the card. |
| The URL `codedapp deploy` printed for your app 404s — *check the app name in the URL* | The live routing slug carries **`-hitl`** (`claim-review-<seat>-hitl`), the name the app was registered under the first time, kept for the life of the registration whatever `-n` says later. Two places hold the true value: the served page's `<meta name="uipath:app-base">` and the entry deploy appended to the shared client (`uip admin external-apps get`). |
| The Action App cannot read the Data Fabric record | It signs in through the shared registration, which is read-only and already exists. Do not create or edit one — `CONFIG.md`. |
| `codedapp deploy` fails `400 Failed to update external client redirect URI` — with **and without** `--client-id` | Deploy reads the client id from the packed `uipath.json`, not the flag, then adds your app's URL to that client — and the shared list is full (`CONFIG.md`, *shared registration*). **Tell the operator; the fix is a prune, not a workaround.** Shipping `clientId: ""` gets past the 400 and empties the platform's meta tags, so whatever fallback config your code holds runs silently in production — measured 2026-08-28: that is how a hand-typed portal URL became a day-long phantom CORS wall. If a fallback exists at all it uses `https://api.uipath.com` and *says on screen* that it is active. |
| The page renders blank; the console says *Invalid SDK instance. Make sure to pass a valid UiPath instance to the service constructor* | `new UiPath()` with no arguments is silently **unregistered** unless the host's meta tags supply a complete config (base URL, org, tenant, client id, redirect URI, scope), and the skill's template builds services at module scope — so the throw happens at import, before any error boundary. Build the session and the services lazily; use `sdk.entities` / `sdk.buckets` (the package root exports no service classes, so the *no dot-chain* rule has no alternative there). |
| A document the record names is *not found* in its bucket | Blob paths are stored with a **leading slash** — `uip or bucket-files list <bucket GUID>` reports `/HO-27088985.pdf` while the record's `*PdfName` column holds `HO-27088985.pdf`. Ask for `/name`, then `name`. `bucket-files` takes the bucket **GUID**; `uip or buckets list` prints both id and key. |
| `uip tasks list` shows every task with `Data: null` | The list never carries payloads; only `uip tasks get <id>` returns `Data.{recordId, claimId, triggerStage}`. And `tasks assign` takes **no** `--folder-key` where `list`, `get` and `complete` all do. |
| Tasks raised earlier stop matching the app you are fixing | Publishing the same app name in two folder contexts registers **two identities under one name**. Existing tasks stay pinned to the first while every deploy upgrades the second. Invisible until you compare a task's app id against your own config. |
| You complete a task from the command line and the claim cannot be re-opened | Every writer replaces the task payload — `contracts/review-task.md`, *What survives completion*. |
| You put the app inside the solution and the case cannot raise a task against it | Measured 2026-08-27 on 1.201.0-preview.127: an in-solution `AppV2` app deploys as a shell — no action schema in the deploy config, `Definition.Id` null, `170000 Failure in the AppTasks request` — and `deploy run` with `externalClientId` appends an anonymous redirect URL to the shared OAuth client per deploy — the 400 it met there was the full list (`CONFIG.md`, *shared registration*), not the shell. Keep the app **beside** the solution, deployed with `uip codedapp deploy --folder-key <seat folder>`; the case binds it by name with that folder as `folderPath` (`CONFIG.md`, *Deploying*). |

## Testing it

**Check the Data Fabric record, not the app.** The app can render beautifully from stale state; the record is what the case actually wrote.

**Build a local Action Center stand-in first — before the screens, not after.** The host speaks postMessage: `AC.init` in, `AC.loadApp` out, then `AC.dataChanged` / `AC.refreshToken` / `AC.complete` / `AC.displayMessage`; `isValidOrigin` in `@uipath/coded-action-app` accepts any localhost origin, so a forty-line page that plays the host lets you read the `AC.complete` payload straight off the wire — the one artefact the case actually consumes and the one no screenshot can check. Measured 2026-08-27: fifteen minutes to build, and it caught the payload defects a live task would have shown only as a wrong record. Two rules it enforces cheaply: **spread the current payload first, then write the contract's names** (the three `inOut` identifiers survive), and **omit an empty output rather than sending `""`** — `""` clears the column on the way to the record.

**`aria-disabled` outcome buttons fail the layout's reachability rule.** The template disables the outcome buttons until the reason is written; Playwright refuses to click them and a screen reader never hears *why*. Keep them enabled, and let a press that is not ready move focus to the reason field and announce the requirement (`role="alert" aria-live="assertive"`).

**Open it in a browser, in both states, before calling it done.** Waiting and decided. A build that passes every command and has never been looked at is not finished, and the two flaws found this way on the reference build were both presentational — raw payload tokens as labels, and a completed-task edge case — which no command would have caught.
