# Design — what bites

| Issue | Fix |
|---|---|
| The planner asks about execution mode, delivery model, agent framework, tools, memory, evaluations, app type, pages or state | Every answer is already in the prompt (*autonomous*; the login resolves the tenant) or in `contracts/components.md` (low-code Agents, no custom tools, no memory, no evaluation sets, one Coded Action App with two screens). Stated, they are not asked. |
| The design lands as `<process-name>-sdd.md`, or as several files | The planner names the file after the process, or splits a Solution into one SDD per project, unless told otherwise. The case build reads **`sdd.md` at the working root** — name it in the request. |
| Types come out matching agents already deployed on the tenant rather than the PDD | The estate sweep runs before the design and a tenant holding a prior build of the same process drives the choices. Name §5.3 in the request; cite `PDD step N.N` in each task's rationale so `check_sdd.py` can verify every one. Record what discovery found — that is a finding, not noise. |
| `AUDIT OK` and you think the design is checked | The planner's audit checks the **shape** only — it passed a table split in two by a blank line and knows nothing about the PDD. `check_sdd.py --pdd` runs that audit *and* checks the design against the process; one command, read both halves of its output. |
| Ten *SME Review* rows, all marked default-carried | Those are decisions made for you and disclosed — read every one. Accept, overrule, or send the contradiction back to the PDD. |
| `## Data Model` and the write-ownership matrix are missing | The planner's template has no data section. `method/sdd-addendum.md` has the two sections to add after Section 4 — `OWN-1` cannot run without them. |
| The build later says *summary SDD* or refuses the file | `uipath-maestro-case` trusts `sdd.md` as written (Rule 2) and refuses a summary: what you owe it is `Status: ready` in the handoff header and `## Section 1: Case Definition` through `## Section 4: Integrations` with the task blocks. The planner's template writes exactly that. |
| Resource ids cannot be resolved and the design stalls | Leave them `<UNRESOLVED>`. Identity resolution belongs to the build, against your own seat. |
| Two conditions carry the same display name — *Stage started* on six tasks, a stage's entry named like its producer's exit | Condition names are **one flat pool across the whole case** — stage entry, stage exit, task entry and case exit — and the validator refuses a duplicate as a hard error at `3d`. Name each one for what it tests, uniquely. |
| A lane is entered on `selected-stage-exited` from a stage that also marks itself complete | The origin completes, so the *exited* event never fires and `3d-case/check_caseplan.py` reports the lane **unreachable**. Route a lane on the origin's **completion** with a guard, and give the next primary stage the exact inverse guard, so the two paths are mutually exclusive. |
| `check_sdd.py` fires on something you believe is correct | Leave it and say so. A wrong rule is worth more to us than a file edited to pass. |

## Reading the checker

`FAIL` reaches the built plan · `WARN` is worth a look and does not stop a build · `NOTE` is something it could not decide, which is never a pass.

`NATURE-3` lists the tasks it could not match to a PDD step. Cite the step in each task's rationale and the list goes to zero; until then the type of those tasks was not checked, whatever the other lines say. `NATURE-1` as a **warning** is expected **four times** on a correct design — on the screening agent for PDD steps 2.1 and 2.4, on the settlement agent (4.3) and on the decision agent (5.1) — because the contract pins those agents although the PDD marks the work rule-expressible; the warning is there so you prove the numbers reproduce.

Three rules shape how the document is *written*, not only what it says, and nothing else describes them: `HANDOFF-3` (no SME review item left `Blocking = yes` — it reads that table's own column), `ACT-1` (how a gateway's task block has to name its Action output), `OWN-1` (the write-ownership matrix and the entity table name the same writers). Read those three in `check_sdd.py` before writing; the rest you meet by reading its output.

`ARG-1`, `JS-1`, `ACT-2` are the three ways an SDD passes both gates and still cannot be built: an `rpa` task bound to an argument the automation does not have — read them from `uip or packages entry-points`, never from memory; a helper called in an `=js:` expression that nothing defines (`nowIso()`, `currencyToCountry(…)`) — the grammar has no helpers, write it inline; a gateway whose outputs never map the platform's literal `Action`. `ROUTE-1` warns on a condition written as `!== …` — unset passes it; `BUDGET-1` warns on an agent with no stated input size *of its own* (quoting the cap is not a budget). `INPUT-1`: an agent, connector or rpa task needs an Inputs **table** — a sentence binds nothing; a design that answered wrong names by deleting the tables passed everything and could not be built. `HANDOFF-4`: the header may say `Template validation | passed` only when the planner's audit does pass — the checker runs it. `BIND-4/5` read every `vars.x`, in `=js:` conditions too. `PROGRESS-1` is a note when `PROGRESS.md` is not beside `sdd.md`. `BIND-7`: an `x = …` output row needs `x` in Case Variables. `ROUTE-2`: the same flag opening a gate on `=== true` and skipping it on `=== false` leaves an unlanded value to neither — the claim stalls; open the human gate on `!== true`. `NATURE-4` warns when no agent block cites §7.9; `BUDGET-2` warns when JSON envelopes reach agents and nothing in the design slices.

**A stage you deliberately do not wire** (Missing details) still has to be valid: a sole task marked `Required: No` under a `required-tasks-completed` exit is refused by `uip maestro case validate` at 3d — *has no task(s) marked as required*. Mark the one task `Required: Yes` and gate the stage's entry on a variable nothing sets.

`SLA-3` compares the **whole-claim** SLA in Case Metadata with the PDD's §5.5 row: a difference you disclosed in *Design Feedback to PDD* is a warning (the PDD is re-baselined before the build binds it), a silent one is a failure. `ENT-1` / `ENT-2` compare the Case Entity with `contracts/claim-entity.md` — a column the design adds is one `3b-entity` will never create, and the first write to it faults three blocks from here; a contract column the design drops is a screen field nobody fills.
